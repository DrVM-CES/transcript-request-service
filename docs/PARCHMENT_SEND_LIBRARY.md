# Parchment Send Library adapter groundwork

This implements a request builder, an INT-only transport and a pure status-notification verifier. No application route, worker, webhook endpoint or provider is enabled. Existing request/SFTP behavior is unchanged. The adapter defaults to disabled and reads no environment variables or credentials. All tests use synthetic data and injected fetch; no actual delivery, email, hosted request or database migration ran.

The credential-free archived delivery specification is dated 230523. Its current-version link was unavailable. The newer supplied endpoint mapping takes precedence: INT is `https://api.int.parchment.com/send-library-api/v1/requestCredentialDelivery`; production is not supported by this adapter. OAuth would use the corresponding `/send-library-api/v1/oauth/token`, but token acquisition is deliberately a supplied port until the contradictory Basic/Bearer client-auth wording is resolved with Parchment. No credential material is included here.

## Implemented behavior

- Required institution sender code, member product code, learner names, learner ID, email, calendar DOB and phone must be supplied. The builder follows the table's `MEMBER_PRODUCT_ID`, including when inconsistent examples use `BASE_PRODUCT_NAME`. It does not split names or infer IDs, dates, products or decoration values.
- Request-only mode omits `image`; it means fulfillment will occur through another process. PDF mode requires explicit decoration status, and a configured decoration ID when decoration is requested. Supplied PDFs/attachments must parse without ignoring encryption, with at most15,000,000 encoded bytes per PDF. This conservative decimal limit and maximum five attachments are local limits. Parsing with pdf-lib is not proof of Apache PDFBox compatibility; real provider validation remains required. No EDI/XML generation is implemented.
- Email/network recipients are distinct. AMCAS mode requires exactly eight-digit AAMC ID and seven-digit transcript ID. Archived known AMCAS IDs cannot silently use generic network mode; the INT adapter refuses the known production AMCAS destination. All sender/product/recipient codes still require provider confirmation for the environment.
- Even explicitly enabled INT transport requires operator-owned learner email and destination allowlists. This matters because Parchment sends learner notifications. Caller input cannot enlarge the configured allowlists or change the constant endpoint. It sends one request, refuses redirects and bounds response bytes/time. No existing server route constructs or enables it.
- `Accepted` returns only accepted, with `deliveryVerified: false`. Unexpected/malformed HTTP or provider responses and post-dispatch failures return `unknown_outcome`. Nothing retries automatically. The archived spec calls externalOrderId unique but does not establish retry/idempotency semantics. Durable dispatch claims and reconciliation must precede wiring this adapter into an application worker.
- Notification HMAC-SHA256 checks the original raw bytes using a constant-time comparison. Encoding must be explicitly selected as hex or base64; there is no assumed default or prefix. These modes are testable implementations, not provider-confirmed live wire format. An expected external order and sender must match; when an existing provider document ID is known it must also match. Unknown events/statuses or invalid signatures return no result. Provider message text is discarded.
- `PENDING` is pending, `APPROVED` processing, `AVAILABLE` available, `DELIVERED`/`COMPLETE` provider-reported delivery, `ERROR` failed and `CANCELLED` cancelled. A valid signed event returns `providerReportedDelivery` but always `deliveryVerified: false` and `reconciliationRequired: true`, including duplicate or older signed events: there is no replay deduplication, event ordering, permanent state update or automaticHTTP200 acknowledgment. Signed events alone do not establish the caller's authority over an MFC order.

## Required before real INT enablement

1. Confirm OAuth client authentication/header/body details, token response schema/reuse/expiry and the current API specification. Supply tokens through a secure server credential path, never browser inputs or logs.
2. Confirm INT sender, member product, decoration and destination identifiers, supported request-only fulfillment, notification routing and any aggregate payload limits. PDFBox processing and actual provider acceptance are untested.
3. Confirm webhook signature encoding/prefix, exact bytes, secret rotation, event registration, replay identifiers and retry/ack behavior. Bind notification reception to the correct environment and durable owner-bound order before applying transitions.
4. Implement durable dispatch and unknown-outcome reconciliation, ownership and authenticated MFC intake, consent/release authority, payload/storage retention and controlled status transitions. No automatic resend follows uncertain acceptance.
5. Verify the existing agreement's INT billing and notification boundaries before testing with synthetic data and configured test recipients. New spending requires founder approval. Production remains outside this adapter.
