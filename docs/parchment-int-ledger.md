## What is implemented

Two additive SQLite/libsql tables hold an immutable MFC order/request identity and
minimal signed provider receipts. The legacy transcript_requests table and SFTP
routes are not changed or interpreted as API orders. Migration SQL does not run
at application startup. The new database must be separately configured; there is
no fallback to the legacy database.

All three Node routes return503 while disabled or outside staging:

- POST `/api/int/orders`: MFC server preparation only; never dispatches. It requires
  an `x-mfc-service-key` and the original learner Bearer token. The token is verified
  using the fixed MFC staging Auth `/auth/v1/user` endpoint, with redirects denied.
  The owner is exclusively the verified response ID, not a body field, referrer,
  query parameter, decoded JWT payload, or stored hint. Body fields are exactly
  mfcOrderId(UUID), requestDigest(lowercase SHA256), releaseReference(1–256 chars).
  Unexpected fields, including ownerId, are rejected. Sender/product come from
  validated server configuration, never request JSON.
- POST `/api/int/order-status`: same two-part authentication; body contains only
  mfcOrderId. Reads filter both verified owner and order; a peer gets404.
- POST `/api/int/parchment-status`: raw-byte HMAC is verified before JSON correlation
  or database access. Signature encoding is explicit, never guessed. Sender,
  external order and document are checked; receipt commits before HTTP200.

**Producer obligation:** MFC must derive the digest from the exact reviewed provider
request and supply an authoritative release reference after its own current
eligibility/consent/order checks. This slice authenticates the MFC caller and owner;
it does not manufacture release authority or verify a digest against a document it
never receives. The MFC producer is not yet wired. Never expose the service key in
the browser, accept it from learner input, or mistake preparation for authorization
to send. A future sender must rebuild/validate the exact payload, recheck release
authority and match the stored digest before claiming. No sender is exposed here.

## Idempotency and recovery

The unique key is (verified owner, MFC order UUID). Identical metadata replays the
stored identity/state; changed digest, release reference, sender or product is a
conflict. Provider externalOrderId is generated by the ledger.

The internal claim seam moves prepared→unknown and commits a unique claim before
it can return any dispatch authority. No route invokes it. Restart, timeout or
retry cannot automatically reclaim unknown/accepted work. Record acceptance only
with the matching committed claim ID; acceptance remains distinct from delivery.
An operator must reconcile uncertain sends with Parchment's documented INT order
history before any separately designed recovery action. There is deliberately no
blind retry, reset-to-prepared or automatic resend API.

Receipts are keyed by SHA256 of exact signed bytes. Only digest, correlation,
document ID, event time, provider enum and receipt time persist; no document,
provider message, signature or secret is retained. Duplicate exact bytes replay
after durable receipt. First valid document ID binds the order; mismatches hold.
Signed older/conflicting statuses remain receipts requiring reconciliation. They
never overwrite dispatch state or set deliveryVerified:true. The supplied guide
does not define ordering or retry guarantees, so eventTime is not authority to
regress or terminalize an order. AVAILABLE is not delivered.

HTTP timeouts may return503 after a database operation has started. If its commit
subsequently succeeds, the next identical request finds the same ledger record;
this is why no success acknowledgment is emitted before commit and no resend is
automatic. Unknown/unclaimed orders or document mismatches receive409 for explicit
reconciliation, not a false receipt acknowledgment. Use a dedicated test setup to
confirm actual provider retry/registration behavior before activation.

## Configuration, deliberately absent by default

`PARCHMENT_INT_LEDGER_ENABLED=true` and `TRANSCRIPT_ENVIRONMENT=staging` are both
required. Required operator settings: PARCHMENT_INT_DATABASE_URL (dedicated migrated
INT database), optional PARCHMENT_INT_DATABASE_AUTH_TOKEN, PARCHMENT_INT_MFC_SERVICE_KEY
(at least32 characters, server-only), PARCHMENT_INT_MFC_ANON_KEY, PARCHMENT_INT_SENDER_CODE
(`1188441`) and PARCHMENT_INT_PRODUCT_CODE (`3228`). Receipt handling additionally
requires PARCHMENT_INT_WEBHOOK_SECRET (at least32 characters) and
PARCHMENT_INT_SIGNATURE_ENCODING exactly hex or base64, confirmed by the provider.
No token-acquisition host, secret or Parchment sending transport is configured here.
Auth calls target only the established MFC staging project; tests replace fetch.

Before a later hosted apply: back up/verify the service database; inspect the exact
new SQL and confirm table names absent; apply once to the dedicated INT target;
verify the existing legacy table/rows are unchanged. Do not run db:push against an
unknown database. Recovery is to disable the three routes and retain ledger
evidence, not drop tables or rewrite historical records. Payload retention and
event reconciliation operations need a reviewed lifecycle before real capture.

## Proof and remaining gates

Actual local libsql tests execute the migration, commit/rollback, two competing
processes, restart/reopen, foreign-owner denial, altered idempotency data,
unauthenticated/forged webhook rejection, exact duplicate receipts, old/conflicting
statuses, document mismatch and deferred-FK COMMIT failures. Both a failed dispatch
claim and a failed receipt commit deny success. Disabled actual Next route wrappers
never open the database. A late Auth result after deadline cannot write.

Native libsql keeps transaction connection handles alive on Windows; tests run in
an isolated child process, then remove the exact temporary directory after process
exit. This is explicit cleanup, not skipped database checks. No environment files,
hosted DB, credentials, email, Parchment transport or paid call is used.
